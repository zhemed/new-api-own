# 解释并核验：内存日志 vs /data/logs 文件日志

## 用户问题（2026-10-07）

面板「服务器日志管理」同时显示：
- `内存日志占用 435 Bytes / 上限 200 MB（1 行）`
- `日志目录: /data/logs ｜ 日志文件数: 5 ｜ 日志总大小: 177.35 KB ｜ 时间范围: 2026-10-06 ~ 2026-10-07`

用户疑问：**「这个文件目录好像是硬盘的呀，你确定是在内存里面吗，为什么有两个日志文件大小」**

## 待核验（真机证据）

1. **用量日志（DB `logs` 表）**：由 `LOG_SQL_DSN=memory` 决定 → 在内存；证据：主库 `one-api.db` 的
   `logs` 行数不再增长 + 接口 `/api/performance/logs` 的内存计数与行数 + 容器启动日志那两行；
2. **应用运行日志文件**：`/data/logs/*.log` 写在**磁盘**上（默认 `-log-dir=/data/logs`，按天轮转）；
   证据：宿主 `/root/data/logs/` 的文件清单与大小；
3. 两者是**不同数据流**：一个是"每条请求的用量记录（面板使用日志/统计的来源）"，
   另一个是"服务运行文本日志（排障用）"——所以有两个大小完全是正常的。

## 可选项（供用户决定，本轮只评估不改）

- 保持现状（推荐：文件日志体积很小，且是内存日志重启丢失后的唯一排障线索）；
- 加启动参数 `-log-dir=` 关闭文件日志（完全靠内存日志 + stdout）；
- 把文件日志指到别处/外挂盘（`-log-dir=/data/...` 或另一个卷）。

## 核验结果（2026-10-07，真机证据）

### 两类日志确实是两条独立数据流

| | 内存日志（用量日志） | 文件日志（应用运行日志） |
|---|---|---|
| 面板行 | `内存日志占用 … / 上限 200 MB（N 行）` | `日志目录 /data/logs ｜ 文件数 ｜ 总大小` |
| 是什么 | 每次调用的**用量记录**（面板"使用日志/用量统计"的数据源） | `[SYS]`/`[GIN]`/`[INFO]`/`[WARN]` 文本日志（排障用） |
| 存放 | **进程内存**（`LOG_SQL_DSN=memory`） | **磁盘** `/data/logs`（在 `./data` 卷内） |
| 重启 | 丢失 | 保留（按天轮转，每次启动新建一个文件） |

### 证据

1. **内存侧在动**：`GET /api/performance/logs` → `bytes=756, rows=2`（此前 435 B / 1 行）——
   计数随使用增长，且只存在于内存；
2. **磁盘侧不动**：主库 `/root/data/one-api.db` 的 `logs` 表**始终 1 行**（不再写入新用量记录）；
3. **容器自证**：启动日志
   `using in-memory SQLite as log database (usage logs are lost on restart)` +
   `LOG_MEMORY_MAX_BYTES=209715200 bytes is trimmed on write (no scheduled cleanup), row cap 200000`；
4. **文件日志实物**：`/root/data/logs/oneapi-<启动时间戳>.log` 共 5 个、合计 200 KB；
   级别统计 `[GIN] 620 / [SYS] 1166 / [INFO] 16 / [WARN] 4` —— 即启动信息 + HTTP 访问日志；
   默认目录来自 `-log-dir`（`common/init.go:22`，默认 `./logs`，容器内落地为 `/data/logs`）。

### 结论

- 用户的观察正确：`/data/logs` **确实在磁盘**——但那是**文件日志**，与"用量日志在内存"并不矛盾；
- **用量日志确实在内存**（有增长计数与磁盘主库不动的双向证据）；
- 文件日志体积很小（200 KB / 5 个），且是重启后唯一排障线索 → 建议保留；
  面板「服务器日志管理」本身提供按数量/天数清理该目录的入口。

## 可选项（待用户决定）

- 保持现状（推荐）；
- 加启动参数 `-log-dir=` 关闭文件日志；
- 把 `-log-dir` 指到别处（如外挂盘/独立卷）。

## 追加评估（用户追问）：保留文件日志会不会影响"日志入内存"的目的？

### 结论：不影响。被去掉的是"重"的那部分，保留的是"轻"的那部分。

| 维度 | 原：DB 用量日志（已改为内存） | 现：应用文件日志（保留） |
|---|---|---|
| 每请求写入 | 1 行 SQLite（0.4–1.0 KB 载荷）+ WAL/页开销 + **事务提交** | 1 行文本 ≈ **99 B/行**（实测），无事务 |
| 是否同步落盘 | 提交路径带同步写（磨损主力） | **无 fsync**：`os.OpenFile(..., O_APPEND|O_CREATE|O_WRONLY)`（`logger/logger.go:56`），由页缓存合批 |
| 体积（实测） | —— | 186,640 B / 1,878 行 / 622 请求 ≈ **300 B/请求**；1 万请求/天 ≈ 45 MB/月 |
| 生命周期管理 | 无（旧方案：无限增长） | 按天轮转 + 面板可手动清理（按天数/N 个文件） |

两者是**互不相干的代码路径**（应用 logger vs GORM 日志库），保留文件日志不会削弱内存日志的任何行为。

### 顺带发现（比文件日志更值得处理）

容器自身 docker json 日志：`/var/lib/docker/containers/<id>/…-json.log` **已 222 KB，且 `max-size` 未设置 → 不轮转、无限增长**。
建议在 `docker run` 上加 `--log-opt max-size=10m --log-opt max-file=3`（需重建容器一次，环境变量原样保留）。

### 若要"零磁盘日志"

- 应用文件日志：`-log-dir=`
- 容器日志：`--log-driver=none`（代价：`docker logs` 不可用）

均不建议在排障需求下启用。
