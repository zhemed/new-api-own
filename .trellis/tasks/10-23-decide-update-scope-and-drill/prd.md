# 就自升级的口径与后续演练征求决定

## 背景

v0.0.43 已交付并升级两端（权限收紧 / ed25519 资产签名 / 不持久提示 / 回滚点；drain 评估后暂缓）。

## 待用户决定

1. **普通管理员能否"看"更新状态**：当前三条 update 路由全部 RootAuth，普通管理员在 `GET /api/status/update` 上也会 403（此前 200）。若希望"能看不能点"，把 GET 单独降回 `AdminAuth`（apply/rollback 仍 root），前端需把"可见"与"可操作"拆开。
2. **回滚演练安排**：`.prev` 是 v0.0.43 新能力，两端由 v0.0.42 升级故无回滚点；真实演练需在下次发布（v0.0.44）时进行。

## 遗留（已在任务记录中）

- 签名密钥换钥必须发版（CI 发现不了 Go 内嵌公钥未更新）；
- 老 Release 无 `.sig` → 从旧版本更新会 502（fail-closed）；
- `.prev` 只保留最近一次；
- `pat_not_allowed` 的 message 为内联双语文本。

## 用户裁定（2026-10-23）

| 问题 | 裁定 | 执行 |
|---|---|---|
| 普通管理员能否查看更新状态 | **保持现状**（GET `/status/update` 也仅 root，普通管理员 403）| 无需改动；前端已按 root 隐藏入口 |
| 回滚演练 | **下次发布（v0.0.44）自动补做** | 记入会话留痕：更新生成 `.prev` → 断言 `rollback_available=true` → 执行回滚 → 贴前后版本与哈希对比，然后重新更新回最新版 |

## 待办清单（下次发布时执行）

1. 发布 v0.0.44 后，对**本地实例**执行面板更新 → 检查 `/new-api.prev` 是否生成、`rollback_available` 是否变 true；
2. `POST /api/status/update/rollback` → 断言 `rolled_back:true` + 版本回退到 v0.0.43 + 二进制哈希与回滚前 v0.0.43 一致；
3. 回滚后再执行一次更新回到 v0.0.44（会重建 `.prev`）；
4. 生成一个**系统访问令牌**后用 PAT 调三个端点，实测 `pat_not_allowed`（补上本轮未完成的 PAT 实机验证）。
