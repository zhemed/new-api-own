# 确认日志模式：内存 vs 落盘

## 背景（2026-10-09 实测触发）

实例升级到 v0.0.11 后，**内存里的用量日志被清空**（更新重启进程）——用户截图中的
`24 t/s / 12 t/s` 记录消失，日志页仅剩一条"登录成功"。这是内存日志模式的固有代价，
v0.0.8 发版说明中已提醒，本次真实触发了一次。

## 待用户决定

| 方案 | 效果 | 代价 |
|---|---|---|
| 保持内存日志（现状）| 省磁盘写入；TPS 上色等前端功能正常 | **每次更新/重启清空用量历史**；内存日志体积上限 200MB、保留 7 天 |
| 改回落盘日志（去掉 `-e LOG_SQL_DSN=memory`）| 历史跨重启保留、更新不清空 | 回到磁盘写入（用户最初想省的正是这部分）|

## 若用户选择落盘

按 README 的部署命令重建容器一次（保留其它四条里的三条变量与 `--log-opt`、
`--network host`、`-v ./data:/data`、`--restart always`），并复核：版本不变、日志表开始落盘、
Docker 日志上限仍生效、面板「日志维护」显示相应状态。

## Acceptance Criteria

- [ ] 记录用户选择
- [ ] 若选择落盘：完成重建并复核四项（版本/落盘生效/日志上限/面板状态）
- [ ] 若保持现状：明确记录"更新会清历史"这一已知代价

## 用户决定（2026-10-09）

**保持内存日志**（`LOG_SQL_DSN=memory` + 200MB 字节预算 + 7 天保留 + 无定时清理）。

接受其已知代价：**每次更新/重启清空用量日志历史**（本次 v0.0.10→v0.0.11 已真实发生一次）。
不做实例改动。若日后要跨更新保留历史，再按 README 部署命令去掉该变量重建即可（文档已同步）。
