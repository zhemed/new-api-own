# 排查自更新签名校验失败

## Goal

用户截图（2026-10-24）：面板弹出「更新到 v0.0.45?」，点击后报错
**「更新包的签名与公布的校验值不匹配，因此已拒绝替换。」**（红条提示）。

需要**只读**查清：这是「发布资产真的不一致（含被篡改/重传）」，还是「校验逻辑、密钥身份、或实例侧缓存的问题」。
本轮**只诊断，不动手修**。

## 已知事实与线索

- 实例当前已在 v0.0.45 正常运行（`/api/status` 200 + `X-New-Api-Version: v0.0.45`，容器由镜像 v0.0.45 重建，
  `restarts=0`），面板却仍提示「更新到 v0.0.45」——版本判定本身可疑。
- 文案 key 位于 `web/src/i18n/locales/zh.json:4358`
  （英文原句：The update signature did not match the published checksum, so the replacement was refused.），
  对应后端错误码应为 `signature_mismatch`。
- 相关实现：`service/update_check.go`（第 38 行注释：签名对象是 SHA256SUMS 文件的原始字节，缺失或验签失败一律拒绝替换）、
  `service/update_apply.go`（第 61 行：老 Release 没有 `.sig` 同样拒绝）、`controller/update_check.go`、`setting/update_check.go`。
- 发布侧：`.github/workflows/release.yml`、`.github/workflows/docker-build.yml`。
- 早期版本（v0.0.43 时代）journal 记录过「资产含 SHA256SUMS.sig」，说明签名链路存在过；
  今天新发的 v0.0.44 / v0.0.45 是否同样带 `.sig`、`SHA256SUMS` 是否与其签名匹配，尚未验证。
- 同仓库刚修过 `scripts/check-version-drift.sh` 的 `v` 前缀比较缺陷 → 怀疑面板的版本判定存在同类问题
  （「有更新」的提示可能是误报，与签名失败是两个独立问题）。

## Requirements

- R1 只读排查，禁止任何写操作：不执行更新、不改配置、不重启、不装包、不调用 POST 路由、不下载大二进制。
- R2 必须查清验签机制：用什么密钥/身份（cosign keyless 的 OIDC 身份与 issuer 约束？固定公钥？），
  `signature_mismatch` 由哪几种条件触发（sig 缺失 / 验签失败 / SHA256SUMS 与下载包不一致 / 其他）。
- R3 必须查清发布侧：v0.0.45 的资产如何产生与签名、是否存在签名后重传或重跑构建导致资产与签名不同步。
- R4 必须查清实例侧：错误上下文（`docker logs`）、`options` 表里的更新检查缓存、容器内 `/new-api` 版本与 `/data` 下是否留有下载产物。
- R5 结论要分清两件事：① 面板为何提示「更新到 v0.0.45」（版本判定）；② 为何签名校验失败（资产/密钥/逻辑）。
- R6 给出影响面判断（是否阻断正常升级、是否有安全含义）与 2-3 个候选修复方向（**不实施**）。
- R7 红线：只读；GitHub 公开页面/API 的只读检索允许（用 `web_fetch`）；不访问其它未点名主机；不碰工作区外文件。

## Acceptance Criteria（收尾回填 2026-10-24）

- [x] AC1 验签机制与触发条件写清：**内嵌公钥的 ed25519 分离签名**（非 cosign keyless、无 OIDC 约束）；
  `signature_mismatch` 的 T1–T5 全部触发条件已穷举，本次命中 **T1「资产缺失」**
  （`service/update_check.go:276、:289-299` 的白名单只有 SHA256SUMS + 两个架构二进制，漏了 `SHA256SUMS.sig`；
  而 `service/update_apply.go:207-212` 在下载任何东西之前就要求它存在 → 条件恒假 → 稳定 502/`signature_mismatch`）。
- [x] AC2 发布侧链路写清：**发布侧无关、资产齐全且自洽**——v0.0.45 四个资产存在
  （new-api-linux-amd64 118513848 / arm64 115474616 / SHA256SUMS 172 / SHA256SUMS.sig 89），
  用官方 asset digest 本地重建 SHA256SUMS 与官方发布值逐字节一致；v0.0.44 同样一致；无签名后重传迹象。
- [x] AC3 实例侧证据齐备：容器进程自报 v0.0.45；`/data` 无 `.prev` 与临时产物；容器内 `/new-api` sha256 ≠ 发布资产 digest
  （旁证从未成功做过下载式自更新）；`options` 表 14 键无 update/version 缓存；`docker logs` 无相关报错（T1 分支不写日志）。
- [x] AC4 根因有证据链且区分「已证实 / 推断」：
  - **已证实**：缺陷自 v0.0.43 引入（提交 `813d5c4`），v0.0.43/44/45 同一份漏项实现 → 面板「立即更新」自 v0.0.43 起 100% 不可用。
  - **推断待验证**：用户那次点击可能发生在「v0.0.45 发布（14:25Z）到本机升级（16:59/17:03Z）」之间的旧构建上，
    或发生在另一实例上（本轮不访问未点名主机，无法闭环）。
- [x] AC5 影响面与候选修复方向：**可用性问题，不是安全退化**（fail closed：被篡改/未签名资产同样被拒；
  镜像升级路线不受影响）；次要风险是文案把「资产缺失」误报为「签名不匹配」且 T1 静默无日志。
  三个候选方向（A 白名单补 `.sig`；B 把裁剪移出共用 fetcher；C 补日志 + 独立错误码 + fetcher→applier 集成回归）已记录，**未实施**。
- [x] AC6 全程只读：未改代码/配置/服务/数据库，未触发任何更新动作；外部证据仅用公开只读检索。

## 结论摘要

| 现象 | 判定 | 说明 |
|---|---|---|
| 报错「签名与公布的校验值不匹配」 | **真代码缺陷（已证实）** | 白名单漏了 `SHA256SUMS.sig`，applier 在下载前就要求它存在 → 恒失败；不是资产问题、不是篡改 |
| 已是 v0.0.45 仍提示「更新到 v0.0.45」 | **未复现（推断）** | 版本归一化会剥 `v`，服务端应为 `up_to_date`；那次点击可能发生在旧构建或另一实例上 |

## Notes

- 本轮不动手修；修复方案待用户点名后再开任务。
- 若根因指向「签名链路本身缺陷」，可能影响所有未来版本的自更新，需要优先处理。
