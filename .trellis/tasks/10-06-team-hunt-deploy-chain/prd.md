# 调查交付链失效模式

## Goal

找出 `tag → 镜像 → 拉取 → 重建容器` 全链路上会导致运行实例停在旧版本的原因，逐条给证据与复现命令。

解决用户核心疑问：**最新版本 `0.0.6` 已发布，但运行中的实例仍是 `0.5`。**

## Requirements

### 已确认事实（上级已核实，本任务不重复验证，仅作为前提）

1. 仓库 `VERSION` = `0.0.6`；
2. registry 的 `latest` / `0.0.6` / `v0.0.6` 指向**同一摘要** `sha256:a74d0a6c…`；
3. 本机缓存的 `latest` 标签**曾经陈旧指向 `0.0.3`**。

> 事实 3 是最关键线索：证明"registry 已更新"**不蕴含**"本机 `latest` 已更新"。

### 必须覆盖的四条调查线

| # | 调查点 | 要回答的问题 |
|---|--------|--------------|
| 1 | registry 侧 | 多架构清单结构如何？别名标签（`latest`/`0.0.6`/`v0.0.6`）是否可能漂移？拉取鉴权是否可能失败？ |
| 2 | **docker 拉取语义（重点）** | 本地 tag 陈旧时，`docker run …:latest` 到底会不会去拉？`--pull=missing/always/never` 与 `docker pull` 的区别？**必须用本机实验证明** |
| 3 | 容器侧 | `--restart always` 与换镜像是什么关系（重启 ≠ 换镜像，必须 `rm` + `run`）？重建时数据卷 / 环境变量有哪些风险？ |
| 4 | 历史 | workflow 里是否存在"只推单架构"或"构建成功但推送失败"的可能？只读查 `.github/workflows/docker-build.yml` + 最近 run |

### 交付物

1. **链路图**（文字版）：从 tag 到运行实例的每一跳，标注"哪一跳引入版本权威"。
2. **失效模式表**：每条含严重度（真实风险 / 理论风险）、"会不会真的导致用户停在旧版本"的判定、证据、复现命令。
3. **实测输出**：docker 拉取语义的本机实验命令 + 原始输出。
4. **一句话结论**：用户停在 `0.5` 最可能的原因。

## Constraints（硬约束 / 红线）

1. 仅允许对 `ghcr.io/zhemed/new-api-own` 做**只读**查询（`docker buildx imagetools inspect`）；
2. **不要** `docker push`；**不要**推送/拉取其它外部资源；
3. **不要触碰用户远程实例**；
4. **不要动 `.local-instance/`**（本机演示实例，别停别删）；
5. **不要 `docker rm` / `docker rmi` 任何东西**；
6. 禁止 `git add -A`、禁止建 git worktree、不 commit / 不 push；
7. **只读**：不修改任何仓库文件（修复由其它成员负责）。

> 受约束 4/5 限制，第 2 项实验**不得**通过删除现有镜像/容器来制造"本地陈旧 tag"，
> 只能用一次性、可丢弃的方式（新建临时 tag 指向旧镜像 / 使用已有陈旧 tag / 只读 inspect）验证拉取语义。
