# 清理镜像删除后释放的 Build Cache（13.26GB）

## Goal

用户点名授权（2026-10-24）：上一轮按桶删除 84 个镜像后，原先与这些镜像共享的缓存层失去引用 →
`docker system df` 的 Build Cache **可回收量从 85.79MB 升到 13.26GB**（总量仍 25.75GB / 429 条）。
执行一次 `docker builder prune -f` 清理，并核验服务无损与实测回收量。

## 授权依据

- 用户在上一轮交付的选择题中勾选「清 Build Cache 13.26GB（推荐）」。
- 属同一天第二次构建缓存清理（上次回收 24.13GB），动作类别已被用户认可；本轮为镜像删除的连带释放。

## Requirements

- R1 只清构建缓存：`docker builder prune -f`（默认语义）；**不加** `--all`，**不用** `docker system prune` 系列；
  不得删除镜像、容器、卷、网络或 `data/`。
- R2 清前基线：`docker system df`、`df -B1 /`、唯一镜像数（26）、标签行（35）、悬空镜像（0）、
  逐容器状态、`new-api` 与 `/api/status`。
- R3 清后核验：`docker system df` 与 `df -B1 /` 前后对比并给出**实测回收字节**；
  **镜像清单必须不变**（26 / 35 / 0）且保留清单关键标签抽样仍在；8 容器全 Up；
  `new-api` running / `restarts=0` / 挂载工作区 / 200 + `v0.0.45`；卷仍 3 个；`data/` 55 文件。
- R4 若回收量明显低于 13.26GB，按共享层/仍被引用的逻辑解释，不要为凑数字加旗标。
- R5 副作用说明：其它项目下次构建失去缓存会变慢（无数据丢失）。
- R6 红线：只动本机、不提交不推送、不升级镜像、不访问外部主机。

## Acceptance Criteria（收尾回填 2026-10-24）

- [x] AC1 实测回收齐备（三口径并列，不凑数字）：预期 13.26GB / prune 自报 13.17GB（99%）/

- [x] AC2 镜像清单不变：唯一 26 / 标签 35 / 悬空 0；保留抽样 12 项全部 KEEP OK

- [x] AC3 服务无损：8 容器全 running；`new-api` running / `restarts=0` / 挂载工作区 / 200 + `v0.0.45`；
      卷 3 个；`data/` 55 文件（Lead 独立复核一致）。
- [x] AC4 副作用与偏差已写明：其它项目下次构建失去缓存命中会变慢（无数据丢失）；
