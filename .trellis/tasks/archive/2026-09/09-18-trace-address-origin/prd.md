# 排查该内网地址为何持续存在并反复进入产物/上下文

## 结论（根因）

该地址不是残留字符串，而是 **harness 的联网搜索代理配置**：

- 用户侧既有配置（2026-09-12）把 `web_search`（tavily 提供方）指向该内网主机的一个 HTTP 端口；
  同一文件内还有该代理的 API Key。
- 被手改过的插件副本里另有 `DEFAULT_BASE_URL` 写死同一地址，是第二份载体。
- 每次 harness 会话启动都会把该地址写进 `/var/log/syslog`（09-12 起共 12 行）。
- 当前会话的项目缓存文件包含整段对话，因此该地址随之被"记住"。

结论：**会话上下文 → 我的输出 → 文件/仓库** 这条链是我这一侧造成的；而**配置 + 插件 + syslog + 会话缓存**
是让它在每个新会话中反复出现的结构性载体。

## 已核实的边界

- 该 API Key 未进入仓库：工作树与全部历史 0 命中。
- 仓库工作树与全部可达历史已无该地址（此前清理 + 历史重写）。
- GitHub 上旧 SHA 的悬空对象仍可访问，彻底清除需联系 GitHub Support。
- 本机临时副本（/tmp 下的克隆、镜像备份、替换表、别名文件、相关 capture）已删除。

## 根除方案（待用户选择）

1. **结构性切断**：把搜索代理改为不出现内网 IP 的形式（本地隧道 `127.0.0.1` 或内部 DNS 名），
   同步把插件里的默认值改回中性值，并删除两份过期 `.bak`。
2. **阻止再次进仓库**：扩展提交闸门（pre-commit / commit-msg / 审计脚本 / CI）增加
   "内网地址 · 密钥样式"检查，命中即拒绝提交——不依赖人记得。
3. **会话侧**：本会话结束后清除其项目缓存；后续使用新会话，不复用已带现场信息的上下文。
4. **GitHub 侧**：整理旧 SHA 清单，按官方流程申请 purge。
